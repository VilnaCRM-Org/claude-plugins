# Degrade matrix

Every capability gap and every safety block the plugin knows has exactly one defined outcome, listed here as the rows D1–D25. Commands, agents and scripts name the row they apply in their escalation blocks and, as `DEGRADED: <note> (D<n>)`, in most degrade notes; a note whose fixed wording carries no id, such as the D5 and D12 notes below, names its condition instead, so a note in a run report still leads straight back to its row. The stages, the run report and the escalation block are described in [the SDLC loop](sdlc-loop.md); the profile keys a row reads (`make.<key>`, `ci.provider`, `review.reviewers`, `review.coderabbit`, `capabilities.run_in_container`, `capabilities.publish_pr_comments`) are described in [the profile schema](profile-schema.md).

## Rules

- The outcome vocabulary is closed: `SUCCESS`, `SUCCESS-WITH-REPORT` and `ESCALATED`, nothing else. `DEGRADED:` is only a line prefix, never a status.
- An absent capability ends `SUCCESS-WITH-REPORT`; a mapped capability that cannot run, or a safety block, ends `ESCALATED`, unless its row names `SUCCESS-WITH-REPORT` for the stage: D13, whose `ask` targets are lifecycle and `-fix` targets and never a gate, and the setup and new-service cells of D2, D3, D5 and D25, which only report what they could not verify.
- Degrade paths never loop and never fake a pass. A target that did not run is listed `<target>: not run (<reason>)`, never `passed`, and is never handed to remediation; the reasons are `capability absent`, `no Docker`, `ask rule`, `no toolchain`, `skipped by triage`, `not changed` and `deferred to PR CI`.
- Where one condition reaches several stages, the Outcome cell names the outcome per stage.
- A degraded stage still meets its exit string; it only reports what it could not verify. A run whose stages all meet their exit strings ends `result: SUCCESS`, with every note in `degrade_notes`.

## Outcome vocabulary

| Outcome | Meaning | In the run report |
| --- | --- | --- |
| `SUCCESS` | the designed path: exit string met, no degrade note | `met: yes`; `result: SUCCESS` |
| `SUCCESS-WITH-REPORT` | exit string met with one or more `DEGRADED:` notes | `met: yes (degraded)`; each note in `degrade_notes`; `result: SUCCESS` |
| `ESCALATED` | the stage stops with the 7-field escalation block | `met: no`; the block in `escalation`; `result: ESCALATED`, and the run ends |

The columns: `#` is the id the degrade notes and escalation blocks cite; Condition is the gap or block; Detected by is the probe, profile value or component that finds it; Outcome is the stage status, per stage where it differs, with the targets-run reason or status line in brackets; Proven by names the bats suite case, the `tests/component-counts.bats` contract id (CC-nn) or the workflow scenario under `tests/fixtures/workflows/` that pins the row. `docs/testing/test-strategy.md` maps every row to its cases.

## What each path does

- **D1, a `null` make key.** The check that needs the key is skipped and listed `<target>: not run (capability absent)`; a `null` key is never replaced by a raw command, and the stage records one note naming the key, for example `DEGRADED: make.docs_check absent: docs-check not run (D1)`. In review a `null` quality row stays `NOT RUN (capability absent)` with its note and does not fail the verdict, and Q7 falls back to the static lane of `security-auditor`; in QA, `make.start: null` skips black-box QA with `SKIP: qa (make.start absent)` and no verdict, which is never reported as a QA pass. Where a stage cannot keep a safety rule without the target (the hook activation before Ralph commits, `make.start` for the container precondition), that stage escalates instead.
- **D2, Docker unreachable.** Docker-dependent work is preceded by `docker info` (in container mode a failing `docker info` of the container precondition is D25, below, and its targets carry the same `not run (no Docker)` reason). A failing probe, or the template message `This target needs a reachable container engine (docker).` in a log, classifies the affected targets `not run (no Docker)`: never `failed` and never remediated, because make exits 2 for any failure and only the message classifies. Implement, review, QA with `make.start` mapped and the new-context C12 gate stages escalate with the `make doctor` output; new-service prints `S8: NOT RUN (no Docker)` with `DEGRADED: container engine unreachable: make bootstrap not run (D2)` and continues with the host toolchain or with `NEXT:` lines.
- **D3, no host toolchain and container mode off.** `command -v cargo` fails while `capabilities.run_in_container` is false, so the targets are `not run (no toolchain)`. Setup records `DEGRADED: no host toolchain and container mode off: make docs-check not run (D3)` at step 8; the loop stages and new-context escalate before their first make target, recommending `/rs-sdlc-setup --exec container` or a host toolchain.
- **D4, protected `.claude/settings.json`.** When `protected-config.toml` lists the file, `merge-settings.sh` writes the allowlist to `.claude/settings.local.json` (or prints it with `--print`), and setup records `DEGRADED: .claude/settings.json is protected (protected-config.toml lists it); allowlist kept in .claude/settings.local.json (D4)`.
- **D5, dirty tracked tree at setup.** Setup does not run `make bmalph-setup` on tracked changes: it prints `DEGRADED: make bmalph-setup not run (tracked changes: <files>)` and `NEXT: commit or stash, then make bmalph-setup`. While `_bmad/` is absent, stage 0 of `/rs-sdlc` then escalates at `setup-check` and names the tracked changes in its `iteration_log`.
- **D6, bmalph absent but installable.** Preflight reports a `WARN: bmalph` row; setup step 2 installs bmalph with `make bmalph-setup` and checks the 2.11.0 floor again. No capability is lost and no note is written.
- **D7, no AI reviewer.** With `review.reviewers: []` and `review.coderabbit: false`, finish-pr uses `ai-review-loop.sh` (or `make <make.ai_review_loop>` when that key is mapped) as the comment source through `pr-comment-resolver`, with `DEGRADED: no AI reviewer — ai-review-loop findings used as the comment source (D7)`; such a pass spends one unit of counter B (`comment_resolution`).
- **D8, no CI.** With `ci.provider: null`, or both check lists empty and zero checks reported, `ci-fixer` is never dispatched, counter A (`ci_fix`) is never spent and finish-pr ends `## Status: SKIPPED-NO-CI` once the rest of its exit string holds; checks a GitHub App still reports are neither fixed nor awaited, each with its D8 note. Zero reported checks while `ci.required_checks` is non-empty is the sensor verdict `WAIT`, never D8.
- **D9, a human-gated block.** A failing check named in `ci.human_gated` makes the sensor answer `BLOCKED`, and an intended breaking contract change without its approval label fails review row Q14. The stage escalates naming the label a maintainer applies (`approved-config-change` or `approved-breaking-change`, as `docs/repository-settings.md` of the service names them); no plugin component applies or removes a label, and a human-gated check is never re-run.
- **D10, `gh` unreachable.** Issue and finish-pr cannot run without `gh` and escalate with the `gh` command and its exit code. Resume reads the state cache instead (`DEGRADED: gh unreachable: state restored from target/rust-sdlc/state/<N>-<slug>.json (D10)`), or starts fresh with review and QA re-run when the cache is absent as well (`DEGRADED: gh unreachable and no state cache: fresh start, review and QA re-run (D10)`). A state record the orchestrator cannot publish is a note, and the cache keeps it; finish-pr escalates on a failing state-comment post instead.
- **D11, no pull request at review time.** The FR/NFR gate runs with `--advisory`, the lens comments are deferred to finish-pr, and review records `DEGRADED: no pull request at review time; FR/NFR gate advisory and review comments deferred to /rs-sdlc-finish-pr (D11)`. The conclusion comment is posted by finish-pr only, on `READY`.
- **D12, comment publishing off.** With `capabilities.publish_pr_comments: false` nothing is posted: the findings stay in the review ledgers, with `DEGRADED: comment publishing off (capabilities.publish_pr_comments: false): review findings stay in the ledgers`.
- **D13, an `ask` rule in a headless run.** A call denied by an `ask` rule of the template (lifecycle and `-fix` targets, never a gate) is recorded `<target>: not run (ask rule)`, never `passed`, and is never retried under another spelling.
- **D14, a call that may exceed 600 s.** Every call outside the foreground allowlist runs in the background and is polled with `wait_log` (the background rule of [the SDLC loop](sdlc-loop.md)). This is the designed path: no note.
- **D15, Claude Code without `--restricted`.** Preflight reports `FAIL` and setup stops with the upgrade remediation; at run time the FR/NFR gate fails fast before it starts its isolated session, and the stage running it escalates.
- **D16, the Python `yq` wrapper on the host.** `have_yq` rejects the kislyuk wrapper and the scripts read YAML with python3 and PyYAML instead; the substitution is transparent and writes no note.
- **D17, template flag off.** New-service imports the template by clone-and-push, prints `IMPORT_PENDING:` and the `NEXT:` advice, and records `DEGRADED: template flag off: clone-and-push import of <slug>@<sha7> (D17)`.
- **D18, sync flavour undecided.** A headless new-service run without `--sync-flavour` prints `SKIP: sync flavour (undecided)` and a `NEXT:` line, and records `DEGRADED: sync flavour undecided: both template-sync workflows kept (D18)`.
- **D19, governance markers missing.** The managed-block marker missing from `CLAUDE.md` or `AGENTS.md` stops stage 0 and the review stage with `run /rs-sdlc-setup on the default branch and commit the result`; setup itself escalates when a marker is still missing after `inject-governance.sh`.
- **D20, not template-derived.** Preflight reports `WARN: template-markers`, the generated profile turns the template capabilities off (`null` keys, `false` flags), and setup records `DEGRADED: not template-derived: <missing markers>; template capabilities off (D20)`.
- **D21, workflow name unresolved.** A nested `workflow()` call that throws (for example `unknown workflow: <name>`) ends the workflow `ESCALATED` with the manual command line that runs the same stage.
- **D22, Ralph's circuit breaker.** Before every `bmalph run`, `ralph_breaker_state` must report `BREAKER: CLOSED` or `BREAKER: ABSENT` with `AUTO_RESET: false`; anything else escalates and nothing runs. After a run, `.state == "OPEN"` in `.ralph/.circuit_breaker_state` or a `STATUS: BLOCKED` status block escalates with the last status block and the last 50 lines of the newest `.ralph/logs/` file. There is never a second `bmalph run`, the breaker is never reset and `.ralph/.ralphrc` is never edited; on resume, `BLOCKED_STAGE: implement breaker=<OPEN|HALF_OPEN>` escalates without running anything.
- **D23, a protected change.** `protected_changes <merge-base-sha>` runs before every commit a command makes, and `make validate-configuration base_ref=<merge-base-sha> CONFIG_CHANGE_APPROVED=` at the implement post-loop and at each review iteration (the branch guards of [the SDLC loop](sdlc-loop.md)). A hit escalates with `blocking_finding: protected file <path> changed (<commit>)` and `recommended_action: revert with git restore --source=<merge-base> -- <path> unless the plan intends it; otherwise approved-config-change`. An agent that needs a protected change stops with its `BLOCKED: protected configuration <path>` line instead of editing; the label is applied by a maintainer, and the edit needs a session restarted with `ALLOW_PROTECTED_CONFIG_EDIT=1`.
- **D24, base ref unavailable.** When `git rev-parse --verify <ci.base_ref>` fails, one `git fetch origin <default_branch>` runs and the check repeats; still unavailable → `base_ref=HEAD`, with a note such as `DEGRADED: base ref <ci.base_ref> unavailable; base_ref=HEAD (D24)`. A failed fetch in the branch step is the same kind of note and never escalates; only a failed `git switch -c` escalates, with `stage: branch`.
- **D25, container mode with `app` not running.** Before the first make target, raw container-route call or hooked git call, `docker compose ps --status running --quiet app` is checked; empty output starts `make.start` in the background (at most 900 s, one restart attempt). A started stack is the designed path. A stack that does not start, or a failing `docker info`, records the targets it blocks `not run (no Docker)`, never `failed` and never remediated, ends setup step 8 with a note such as `DEGRADED: app container not running: make docs-check not run (D25)`, makes new-service print its remaining steps as `NEXT:` lines and stop, and escalates the loop stages and new-context.
